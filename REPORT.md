## 2. Attack Types Simulated and How

### Defined attack taxonomy (`backend/app/ml/attack_taxonomy.py`)
Six classes with hand-tuned numeric ranges used only for training-data generation:

| Class | packet_rate | bytes_sent | unique_ports | failed_logins |
|---|---|---|---|---|
| normal | 1–5 | 100–500 | 1–2 | 0 |
| port_scan | 20–50 | 200–800 | 20–100 | 0 |
| ddos | 200–1000 | 10000–50000 | 1–3 | 0 |
| bruteforce | 10–30 | 500–2000 | 1–2 | 10–100 |
| sql_injection | 5–15 | 2000–8000 | 1–2 | 0–2 |
| malware | 50–150 | 5000–30000 | 3–10 | 0 |

### What is actually generated at runtime
The background loop (`services/auto_attack.py`) generates **only two traffic types** every 8–12 seconds:
- 40 rows of **port_scan** via `scripts/generate_port_scan_attack.py`
- 60 rows of **normal** traffic via `scripts/generate_normal_traffic.py`

Generation method is pure Python `random` within fixed ranges — **no packet capture, no Scapy, no pcap replay**. All other attack types (DDoS, bruteforce, SQL injection, malware) exist in the taxonomy but are never emitted by the live pipeline.

## 3. Detection Mechanism — Data Flow and Critical Findings

### Data flow (end-to-end)

```
auto_attack_loop() [every 8-12 s]
  │
  ├─ generate_port_scan(n_ports=40)   → data/raw/port_scan.csv
  └─ generate_normal_traffic(n=60)   → data/raw/normal_traffic.csv
        │
        ▼
DetectionEngine.run_once()
  │
  ├─ load_all_logs()                  ← reads all CSVs from data/raw/
  ├─ aggregate_by_time_window(5 s)    ← computes 4 features per IP/window:
  │      packets_per_second, avg_request_rate, failed_connections, unique_ports
  │
  ├─ model.predict(X)                 ← Random Forest classifies each row
  │      → predicted_label: "normal" or one of the attack classes
  │
  ├─ Filter: keep rows where predicted_label != "normal"
  │      (model output IS used to gate whether anything is flagged)
  │
  └─ For each flagged row:
       ├─ label   = random.choice(possible_labels)    ⚠ MODEL OUTPUT DISCARDED
       ├─ tier    = random.choices(['block','rate_limit','monitor'], [30,40,30])
       ├─ risk_score   = random range by tier (45–98)  ⚠ RANDOM
       ├─ confidence   = random range by tier           ⚠ RANDOM
       ├─ severity     = fixed by tier                  ⚠ RANDOM
       └─ evaluate_and_respond() → policy decision → audit log → detections.csv
```

### Is there a real trained ML model?

**Yes and no.**

- `models/random_forest.pkl` exists and is a genuine `sklearn.ensemble.RandomForestClassifier` with 100 estimators, loaded and called via `joblib`.
- It was trained on data generated by `dataset_generator.py`, which itself uses the hand-crafted numeric ranges in `attack_taxonomy.py` — **not real network captures**.
- **Critical feature mismatch:** training data columns are `[packet_rate, bytes_sent, unique_ports, failed_logins]` (from `dataset_generator.py`), but inference uses `FEATURE_COLUMNS = [packets_per_second, avg_request_rate, failed_connections, unique_ports]` (`feature_engineering.py`). The model was serialized after training on a different column set. Predictions may still run (sklearn doesn't enforce column names on `predict`) but the model is being fed mismatched features.
- After the model returns a prediction, `detection_service.py:80` immediately discards it: `label = random.choice(possible_labels)`. The model's classification of *which* attack type is never used.

### `seed_detections.py` — demo data only

This root-level script generates **completely random rows** (random IP, random label, random action, random timestamp) and appends them to `detections.csv`. There is no model or logic involved. It exists solely to pre-populate the dashboard for demonstration purposes.

### Verdict

**Detection is partially real, partially demo scaffolding:**
- The Random Forest is real but trained on synthetic data with a feature name mismatch.
- It correctly gates detections (only attack-predicted rows produce alerts), but its attack-type classification output is thrown away.
- All metadata written to `detections.csv` (label, risk score, confidence, action) is randomly generated — it is **demo data, not ML output**.

## 4. The "Action" System — What It Actually Does

### Decision engine (`response/decision.py`)

A rule-based escalation ladder applied after the (random) risk score is determined:

| Condition | Decision |
|---|---|
| IP in whitelist | ALLOW |
| IP in hard-block file and block unexpired | BLOCK |
| severity == "critical" | BLOCK + hard-block 1 hour |
| IP reputation score ≥ 200 | BLOCK |
| attack_rate ≥ 5/min | BLOCK + hard-block 30 min |
| attack_rate ≥ 1/min | RATE_LIMIT |
| attack_count ≥ 5 | MONITOR |
| severity == "medium" | MONITOR |
| otherwise | ALLOW |

Reputation scores accumulate across detections and decay 30% per 24-hour idle period. Hard blocks expire after their duration.

### Enforcement layer (`response/actions.py`)

The docstring reads "Simulated enforcement layer." All three actions return a success dict but perform **no system calls**:

- `firewall_block` → returns `"IP blocked by simulated firewall rule"` — does not touch `iptables`, `pf`, `nftables`, or any OS firewall.
- `log` → returns `"Event logged for monitoring"` — the actual write happens upstream in the audit writer.
- `throttle` → defined but never reached in the current decision mapping (the mapping converts RATE_LIMIT to `"log"`, not `"throttle"`).

### What is persisted
- `detections.csv` — append-only detection log.
- `data/audit/security_events.jsonl` — structured audit trail (JSON lines).
- `backend/app/policy/hard_blocked_ips.json` — temporary IP blocks with expiry timestamps.
- `data/policies/ip_reputation.json` — cumulative reputation scores.
- `data/policies/ip_last_seen.json` — last-seen timestamps for decay.

**Summary:** decisions and audit trails are logged faithfully, but no traffic is actually blocked, rate-limited, or throttled on the host network.

## 5. Known Gaps, TODOs, and Incomplete Features

### Critical correctness issues

1. **Predicted attack label is discarded** (`detection_service.py:80`). The model's classification output is never used to set the `label` field — a `random.choice` replaces it.

2. **Feature column mismatch between training and inference.** `dataset_generator.py` produces `[packet_rate, bytes_sent, unique_ports, failed_logins]`; inference reads `[packets_per_second, avg_request_rate, failed_connections, unique_ports]`. The model is predicting on structurally different features than it was trained on.

3. **Risk score and confidence are randomly generated**, not derived from model probability output (`predict_proba` exists but is never called in the live pipeline).

4. **Only port_scan is simulated at runtime.** Five of the six attack classes exist only in the training data generator and dashboard labels — they are never actually generated as traffic.

5. **Two separate hard-block files with different paths:**
   - `response/decision.py` reads/writes `backend/app/policy/hard_blocked_ips.json`
   - `response/hardlock.py` reads/writes `data/processed/hard_blocked_ips.json`
   - `routes_system.py` reads from `data/policies/hard_blocked_ips.json`
   These three modules are not coordinated and may show inconsistent block states.

6. **`RATE_LIMIT` decisions map to `"log"` action** in `response/engine.py`, not `"throttle"`. The throttle path in `actions.py` is dead code.

### Missing data and infrastructure

7. **`data/training/attack_dataset.csv` does not exist** in the repo. The model was trained but the training data was not committed. Retraining is not possible without re-running `build_dataset.py`.

8. **`data/policies/whitelist_ips.json` and `data/policies/policies.json`** are referenced but may not exist. The code creates them empty on first use, silently defaulting to no policy rules.

9. **`data/audit/decision_audit.csv`** is read by `routes_system.py` for the system overview dashboard, but nothing in the codebase writes to that file (audit writes go to `security_events.jsonl`). The system overview counts will always be zero unless this file is manually created.

10. **`backend/app/policy/engine.py`** (the older `enforce_policy` function) is defined but never called by any active code path. The active policy logic is in `response/decision.py`.

### UX / architecture gaps

11. **No WebSocket or server-sent events.** The frontend polls on a timer; there is no push channel, so the dashboard lags behind real events.

12. **`seed_detections.py` generates purely random data.** Running it populates the dashboard with labels, actions, and IP addresses that have no relationship to actual model output.

13. **No model versioning or retraining trigger.** The `.pkl` file is static; there is no API endpoint or scheduled job to retrain as new detections accumulate.

14. **DDoS, bruteforce, SQL injection, malware attack simulation is absent** from the live pipeline. The dashboard can display these labels only because they are randomly assigned.

## 6. What Would Need to Change for a Real ML-based IDS + Automated Response

### Step 1 — Fix the training / inference feature contract
- Align `FEATURE_COLUMNS` in `feature_engineering.py` with the columns produced by `dataset_generator.py`, or rebuild the aggregation pipeline to emit the same features the model was trained on.
- Alternatively, re-generate a proper training dataset from the live aggregation output (let `aggregate_by_time_window` produce the training rows directly).

### Step 2 — Use the model's output
- Replace `label = random.choice(possible_labels)` with `label = row["predicted_label"]` (the actual model prediction).
- Replace the random `risk_score`/`confidence` tiers with `predict_proba` output: `confidence = model.predict_proba(X)[i].max()`.

### Step 3 — Generate all simulated attack types
- Extend `scripts/` to emit DDoS, bruteforce, SQL injection, and malware traffic patterns (synthetic but at least consistent with the training taxonomy).
- Alternatively, ingest real-world traffic captures (CICIDS2017, NSL-KDD, UNSW-NB15) as the training and simulation source.

### Step 4 — Real network enforcement
- Replace the stub in `actions.py` with actual OS-level calls:
  - Linux: `python-iptables` or `nftables` via subprocess
  - macOS: `pfctl` via subprocess
  - Cloud: AWS Security Group / GCP Firewall API calls
- Add rollback/unblock logic tied to the hard-block expiry timestamps already in the policy engine.

### Step 5 — Fix the audit pipeline
- Write decision audit records to `data/audit/decision_audit.csv` so that `routes_system.py` reads live data.
- Or refactor `routes_system.py` to read from `security_events.jsonl` instead.

### Step 6 — Retrain on real data
- Replace the synthetic taxonomy-range generator with real labeled datasets.
- Add a training pipeline trigger (manual or scheduled) that retrains from `data/processed/detections.csv` as ground-truth feedback accumulates.

### Step 7 — Real-time dashboard
- Add a WebSocket endpoint (FastAPI natively supports this) so the frontend receives events as they are logged rather than polling.

### Step 8 — Resolve the hard-block path split
- Consolidate `response/decision.py`, `response/hardlock.py`, and `routes_system.py` to read/write a single canonical hard-block file at one agreed path.

## Summary

The project has a solid architectural skeleton: a FastAPI backend, a React frontend, an ML training pipeline, a rule-based decision engine, a reputation system, and an audit trail. The main gap is that the live detection pipeline does not actually use the model's output — labels, risk scores, and confidence values are randomly generated at runtime, making the current dashboard display demo data only. The ML model exists and is called, but its classification is discarded immediately after the binary "is this an attack?" gate. No host-level enforcement occurs; all block/rate-limit actions are simulated in-process. Closing the feature-alignment bug, wiring the model's `predict_proba` output into the detection record, and adding even a subprocess call to the OS firewall would turn this from a demo into a functional prototype IDS.
